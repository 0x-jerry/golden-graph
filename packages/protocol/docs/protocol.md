# Backend ↔ Core protocol

This document is the authoritative reference for every protocol between the
core (`@0x-jerry/golden-graph`) and the backend
(`@0x-jerry/golden-graph-backend`). Types are defined in
`packages/protocol/src/ExecutorBackend.ts`, `packages/protocol/src/jsonrpc.ts`,
`packages/protocol/src/ExecutorRpc.ts`, `packages/protocol/src/types.ts`,
`packages/protocol/src/NodeSchema.ts` and `packages/protocol/src/NodeProvider.ts`.

## 1. Overview & invariants

The core and the backend talk over **JSON-RPC 2.0**
(https://www.jsonrpc.org/specification). Every message is a plain-JSON
Object; there is no shared object graph across the boundary — every payload
must survive a `JSON.parse(JSON.stringify(...))` (equivalently: a
`structuredClone`) round trip.

Invariants that the whole protocol is built on:

- **Core never executes** — workflows always run on the backend. The frontend
  renders the graph, sends a snapshot, and applies the values the backend
  streams back.
- **Backend never renders** — it walks the snapshot directly and has no
  `Workspace`/`Node` instances. Node shapes come from the schemas it serves via
  `goldenGraph/listNodeProviders`.
- **Node/edge/group ids are stable across snapshots** (`extra.incrementID` in
  the snapshot). The backend's diff cache is keyed by node id and relies on
  this.
- **Enums are numbers** (JSON-safe): `HandlePosition` `None=0/Left=1/Right=2`,
  `NodeType` `None=0/Entry=1`.
- **Execute functions are worker-safe** — no DOM access. Handle values written
  during execution must be structured-cloneable.

## 2. JSON-RPC 2.0 subset

The protocol implements the JSON-RPC 2.0 spec (§4 request, §5 response/error,
§4.1 notification) and deliberately deviates/omits the rest:

- **Version marker** — every message carries `"jsonrpc": "2.0"`.
- **Requests** — `{ "jsonrpc": "2.0", "id", "method", "params"? }`. `id` is an
  integer generated by the client (Numbers SHOULD NOT have fractional parts;
  Null ids are discouraged by the spec and never generated). `params`, when
  present, is always a by-name Object (§4.2) — bare, never wrapped. A Request
  carrying `id: null` is rejected as Invalid Request (§5's "undetectable id"
  case — the client never generates such ids).
- **Responses** — `{ "jsonrpc": "2.0", "id", "result" }` or
  `{ "jsonrpc": "2.0", "id", "error": { "code", "message" } }`. Exactly one of
  `result`/`error`; `id` echoes the request id. Invalid requests reply
  `id: null` (§5).
- **Notifications** — `{ "jsonrpc": "2.0", "method", "params"? }` (no `id`).
  The server MUST NOT reply to a Notification (§4.1).
- **Error codes** (§5.1) — the standard pre-defined codes plus the
  implementation-defined server-error range:

  | code | meaning | used for |
  | --- | --- | --- |
  | `-32700` | Parse error | never over structured-clone transports (no textual JSON parsing happens); reserved for future textual channels |
  | `-32600` | Invalid Request | malformed messages, top-level Arrays (batch), Requests with `id: null` |
  | `-32601` | Method not found | unknown method names |
  | `-32602` | Invalid params | (reserved, not currently emitted) |
  | `-32603` | Internal error | (reserved, not currently emitted) |
  | `-32000` | Server error | failed workflow runs; `message` is the thrown error's message |
  | `-32001` | Cancelled | the run was stopped by `goldenGraph/cancel`; `message` is `'cancelled'` |

- **Batch (§6)** — out of scope: the client never sends Arrays, and the
  server rejects a top-level Array as a single Invalid Request.
- **Method names** — namespaced `goldenGraph/<method>`. The spec only reserves
  the `rpc.` prefix (§4, §8), so this namespace is free.

The shared implementation lives in `packages/protocol/src/jsonrpc.ts`
(`JsonRpcClient`, `JsonRpcServer`, type guards, error constants) with the
method contracts in `packages/protocol/src/ExecutorRpc.ts`.

## 3. Transport layers

The protocol is transport-agnostic. Two layers share the same JSON-RPC
messages:

| Layer | Core side | Backend side | Notes |
| --- | --- | --- | --- |
| In-process | `ExecutorBackend` interface | `WorkflowExecutor` (via `DirectExecutorBackend` test helper) | A `JsonRpcClient`/`JsonRpcServer` looped back in-process; payloads are structured-cloned to mimic real transport. |
| Web Worker | `WorkerExecutorBackend` | `ExecutorWorkerHost` | `postMessage` payloads are exactly the JSON-RPC messages described below. |
| Any out-of-process channel | any `ExecutorBackend` impl | any process (any language) | Speak the same JSON-RPC methods over e.g. WebSocket. |

### The `ExecutorBackend` contract (in-process)

```ts
interface ExecutorBackend {
  /** All node providers (id + name + schemas) this backend defines. */
  getNodeProviders(): Promise<INodeProvider<INodeSchema>[]>

  /** Run a workflow. Resolves after the run finished; rejects on failure. */
  execute(req: ExecuteRequest, onEvent: (e: ExecutorBackendEvent) => void): Promise<void>

  /** Request the in-flight run to stop. Fire-and-forget; a no-op when idle. */
  cancel(): void

  /** Tear down (e.g. terminate the worker). */
  dispose?(): void
}
```

The interface is an ergonomic facade; the contract it implements is defined
in JSON-RPC terms: `getNodeProviders()` maps to the
`goldenGraph/listNodeProviders` Request, `execute()` maps to the
`goldenGraph/execute` Request, `onEvent` receives the
`goldenGraph/progress` / `goldenGraph/handleUpdates` Notifications, and
`cancel()` sends the `goldenGraph/cancel` Notification. Each
implementation is a thin adapter over `JsonRpcClient`.

`execute()` resolves **only after all events for the run were delivered** and
rejects when the run failed. Transports settle that promise from the
`goldenGraph/execute` Response. A cancelled run **rejects** with a
`CancelledError` (`code: -32001`, message `'cancelled'`) — cancellation is a
distinct outcome from success and failure, so callers can treat it as the
user action it is (`isCancelledError(error)`).

### Worker transport specifics

- `WorkerLike` (frontend side) and `WorkerScopeLike` (worker side) are
  structural subsets of the DOM worker types — they keep the backends testable
  in jsdom and in-process.
- The worker entry creates an `ExecutorWorkerHost` and registers the node
  providers via `addProviders`:

```ts
import { ExecutorWorkerHost } from '@0x-jerry/golden-graph-backend'
import { nodeProviders } from './nodes'

const host = new ExecutorWorkerHost()
host.addProviders(nodeProviders)
```

- The frontend attaches it with `WorkerExecutorBackend`:

```ts
import { WorkerExecutorBackend } from '@0x-jerry/golden-graph-backend'

const worker = new Worker(new URL('./executor.worker.ts', import.meta.url), {
  type: 'module',
})
const workspace = new Workspace({ executorBackend: new WorkerExecutorBackend(worker) })
await workspace.loadNodeProvidersFromBackend()
```

## 4. RPC method catalogue

### `goldenGraph/listNodeProviders` (Request)

Ask the backend for every node provider it defines. No `params`. Answered with
`result: { providers }`. Sent once during
`workspace.loadNodeProvidersFromBackend()`.

Request:

```json
{ "jsonrpc": "2.0", "id": 1, "method": "goldenGraph/listNodeProviders" }
```

Response:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "providers": [
      {
        "id": "Math",
        "name": "Math",
        "nodes": {
          "Op": {
            "type": "Math.Op",
            "name": "Math - Op",
            "handles": [
              { "key": "a", "name": "A", "position": 1, "accepts": "number", "value": 0 },
              { "key": "out", "name": "Sum", "position": 2, "accepts": "number", "value": 0 }
            ]
          }
        }
      }
    ]
  }
}
```

### `goldenGraph/execute` (Request)

Run a workflow. `params` is the `ExecuteRequest` (bare — not wrapped):

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "goldenGraph/execute",
  "params": {
    "snapshot": {
      "version": "1.0.0",
      "extra": { "incrementID": 3 },
      "coordinate": { "origin": { "x": 0, "y": 0 }, "scale": 1 },
      "nodes": [
        { "id": 1, "type": "Number", "data": { "out": 1 }, "pos": { "x": 0, "y": 0 } },
        { "id": 2, "type": "Math.Op", "data": { "a": 0, "b": 0, "out": 0 }, "pos": { "x": 200, "y": 0 } }
      ],
      "edges": [
        { "id": 1, "type": "default", "start": { "id": 1, "key": "out" }, "end": { "id": 2, "key": "a" } }
      ],
      "groups": [],
      "subGraphs": []
    },
    "entryNodeIds": [1],
    "debug": false
  }
}
```

`ExecuteRequest`:

```ts
interface ExecuteRequest {
  /** Full workspace snapshot (`workspace.toJSON()`). */
  snapshot: IWorkspace
  /** Ids of the entry nodes the run starts from. */
  entryNodeIds: number[]
  /** Mirrors `workspace.state.debug`; backends should pace execution. */
  debug: boolean
}
```

During the run the backend streams Notifications (below); when the run
completes it replies to the Request — the Response **is** the run
settlement:

Success (the run finished; all Notifications already delivered):

```json
{ "jsonrpc": "2.0", "id": 2, "result": null }
```

Failure (the run threw; the frontend rejects `execute()` with
`new Error(message)`):

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "error": { "code": -32000, "message": "boom" }
}
```

Cancelled (the run was stopped by `goldenGraph/cancel`; the frontend
rejects `execute()` with an error carrying `code: -32001`, recognizable
via `isCancelledError()`):

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "error": { "code": -32001, "message": "cancelled" }
}
```

There is no `finish` message — settlement lives in the Response.

### `goldenGraph/progress` (Notification)

A node started processing. `params: { "currentNodeId": <number> }`. The
frontend mirrors this into `executorState.currentNodeId` (`-1` when idle).

```json
{ "jsonrpc": "2.0", "method": "goldenGraph/progress", "params": { "currentNodeId": 1 } }
```

### `goldenGraph/handleUpdates` (Notification)

Handle values written by processed nodes, batched per node.
`params: { "updates": HandleValueUpdate[] }`:

```json
{
  "jsonrpc": "2.0",
  "method": "goldenGraph/handleUpdates",
  "params": {
    "updates": [{ "nodeId": 2, "key": "out", "value": 1 }]
  }
}
```

```ts
interface HandleValueUpdate {
  nodeId: number
  key: string
  value: unknown
}
```

The frontend applies each with `node.setData(key, value)` so
`handle:updated` events keep flowing exactly like a local run.

### `goldenGraph/cancel` (Notification)

Ask the backend to stop the in-flight run. No `params`; the server MUST
NOT reply. Idempotent and a no-op when no run is running or the run
already settled: the cancellation targets only the run in flight when the
message arrives, so a cancel that races past the end of a run never
affects the next one (each run owns a fresh `AbortController`).

```json
{ "jsonrpc": "2.0", "method": "goldenGraph/cancel" }
```

The run stops cooperatively at its next node boundary and settles its own
`goldenGraph/execute` Response with the `-32001` Cancelled error above —
there is no separate cancel-acknowledgement message. Note the
single-thread limitation: a long **synchronous** node execute blocks the
worker's message loop, so the cancel is only delivered once the worker
next yields (debug-mode runs pace with sleeps and cancel promptly).

### Correlation & concurrency

- Request ids are integers generated by the client; the server echoes the
  same `id` in the Response (§5). The client matches pending calls by id.
- The worker transport serializes operations: `getNodeProviders()` and
  `execute()` each reject re-entrant calls ("already in flight" /
  "already executing"), so at most one run streams Notifications at a time.
  The host dispatches Requests immediately and trusts the client to
  serialize runs — a concurrent second `goldenGraph/execute` would
  interleave the executor's diff cache and is not guarded server-side.
- Notifications are discriminated from Responses by the **absence of `id`**
  (§5), never by `result`/`error` presence.

## 5. Node discovery protocol

### `INodeProvider<INodeSchema>`

```ts
interface INodeProvider<T> {
  /** Unique provider id. An EMPTY id registers flat (non-namespaced) nodes. */
  id: string
  /** Display name — drives the "Add Node" submenu label in the renderer. */
  name: string
  /** Nodes keyed by local name; the node type is derived from id + key. */
  nodes: Record<string, T>
}
```

The backend owns node *definitions* (`INodeDefinition = { schema, execute }`)
and registers them in providers (`INodeProvider<INodeDefinition>`). When
serving the frontend, the execute functions are stripped and only the
schemas travel over the wire.

### Auto-generated node types

A node's `type` is **derived** from its provider id and record key:

```
type = id ? `${id}.${key}` : key
```

Examples:

| provider id | key | type |
| --- | --- | --- |
| `'Math'` | `'Op'` | `'Math.Op'` |
| `''` (flat) | `'Number'` | `'Number'` |
| `'subgraph'` | `'input'` | `'subgraph.input'` |

A provider whose schema already carries a `type` that differs from the derived
value is a configuration error and the registration throws. `type` is optional
on an authored schema; `Workspace.registerNodeSchema()` (direct, no provider)
still requires it.

### `INodeSchema`

```ts
interface INodeSchema {
  type?: string        // auto-filled by the provider; required for direct registration
  name: string         // node header + "Add Node" menu label
  description?: string
  internal?: boolean   // hidden from the "Add Node" menu
  nodeType?: NodeType  // NodeType.Entry = 1 marks an execution start
  handles: INodeHandleConfig[]
}
```

`INodeHandleConfig`:

```ts
interface INodeHandleConfig {
  key?: string                 // unique within node; edge loc key uses it
  accepts?: string | string[]  // data type(s) for connection matching; '*' = any
  type?: string                // render component: 'text' | 'number' | 'select' | 'image' | 'display'
  name?: string                // handle label
  description?: string         // shown in a tooltip on hover
  position?: HandlePosition    // Left = input, Right = output, None = layout-only row
  value?: unknown              // initial value
  options?: Record<string, any> // render props (select choices in options.options)
}
```

### Internal (subgraph interface) nodes

`subgraph.input` / `subgraph.output` are core-owned schemas registered through
a **core-side `subgraph` provider** (`subGraphNodeProvider` in
`SubGraphSchema.ts`); the backend registers the matching definition provider so
its executor can process them. They are `internal: true` (never shown in the
Add Node menu) and are **not served** over `goldenGraph/listNodeProviders` —
the frontend registers them itself in the `Workspace` constructor.

### Frontend registration flow

1. `workspace.loadNodeProvidersFromBackend()` →
   `backend.getNodeProviders()` (the `goldenGraph/listNodeProviders` Request).
2. Each returned provider is normalized (types stamped) and registered with
   `workspace.registerNodeProvider(provider)`.
3. `ws.providers` exposes them in registration order; the renderer's
   "Add Node" context menu groups nodes under `provider.name` submenus,
   skipping `internal` schemas and empty groups.

## 6. Execution protocol

### The snapshot (`IWorkspace`)

```ts
interface IWorkspace {
  version: string                          // for data migration
  extra: { incrementID: number }           // next free id — keeps ids stable across snapshots
  coordinate: { origin: { x, y }, scale: number }
  nodes: INode[]
  edges: IEdge[]
  groups: IGroup[]
  subGraphs: ISubGraph[]                   // recursive — each has its own IWorkspace
}
```

```ts
interface INode {
  id: number
  type: string
  data?: Record<string, unknown>   // real (non-edge-resolved) handle values
  subGraphId?: number              // set on collapsed subgraph nodes
  pos: { x: number, y: number }
  size?: { x, y }                  // 0/missing = auto
  collapsed?: boolean              // header-only render; joints hidden, edges
                                   // dock at the header line (missing/false = expanded)
}

interface IEdge {
  id: number
  type: string
  start: INodeHandleLoc
  end: INodeHandleLoc
}

interface INodeHandleLoc {
  id: number     // node id
  key: string    // handle key
}
```

Handle locations are canonically keyed as `edgeLocKey(loc) = \`${id}:${key}\``.
The backend indexes edges by this key to resolve connections.

### Backend execution semantics

The reference engine is `WorkflowExecutor` (backend). Backends in other
languages should replicate:

- **Traversal** — stack-based, starting from the entry nodes
  (`nodeType === NodeType.Entry`). A node is re-queued until all upstream nodes
  (sources of edges into its input handles) have been processed. A loop guard
  (`MAX_ITERATIONS = 100_000`) throws on unresolvable dependency cycles.
- **Input resolution** — a left (input) handle connected by an edge reads the
  connected right (output) handle's *current* value; otherwise it reads its
  local value. `ctx.getData(key)` returns this; `ctx.setData(key, value)` writes
  the run state and accumulates a `handle-updates` batch (streamed as
  `goldenGraph/handleUpdates` Notifications).
- **Diff cache** — keyed by node id. A node re-executes only when its
  fully-resolved data changed since the last successful run; unchanged nodes
  are skipped and their cached outputs carry forward.
- **Subgraph nodes** (`INode.subGraphId != null`) — the collapsed node's handle
  keys are the nested workspace's interface node *ids*. Execution injects the
  node's inputs into the nested `subgraph.input` nodes, runs the nested
  workspace (lazy child executor, silent events, own diff cache), then reads
  the `subgraph.output` nodes' `Value` back onto the node's output handles.
- **Debug mode** — sleeps (100 ms per changed node) so progress stays
  observable.
- **Unknown node types** throw at runtime so misconfigured graphs fail loudly.
  Subgraph interface nodes never hit this path because the backend always
  registers the internal `subgraph` provider.

### Frontend orchestration

`Workspace.execute()` (`Executor` facade): guards re-entrancy, snapshots the
workspace, sends `goldenGraph/execute`, and translates events:

- `progress` → `executorState.currentNodeId` + `executor:changed`.
- `handle-updates` → `node.setData(key, value)` on the live nodes.
- the `execute` Response → settlement via the promise; the facade never
  re-wraps the rejection. Across the JSON-RPC boundary the error's
  `message` and `code` travel — the client rethrows `new Error(message)`
  with the `code` re-attached — so the original error's `name`/`stack` do
  not survive a round trip, but implementation-defined codes do (this is
  how a cancelled run stays recognizable as `-32001` after crossing the
  worker). True for both the worker transport and the in-process
  `DirectExecutorBackend`, which speaks the same protocol.

## 7. JSON-safety & constraints

- Every message payload is plain JSON — no class instances, no functions, no
  `undefined`-only semantics relying on transport-specific behavior.
- Enums (`HandlePosition`, `NodeType`) serialize as their numeric values.
- Execute functions never run on the frontend; they run in the worker and must
  be DOM-free.
- Handle values (initial `value`, runtime `setData` writes,
  `goldenGraph/handleUpdates` payloads) must be structured-cloneable.
- Ids are generated starting at 1 (`createIncrementIdGenerator`) and persist via
  `extra.incrementID` — never assume sequential ids are gap-free, but do assume
  a node id always refers to the same node across snapshots. (JSON-RPC request
  ids are unrelated and come from `JsonRpcClient`'s own counter.)

## 8. Lifecycle

- `dispose()` rejects in-flight calls and terminates the worker transport.
- **Dispose ordering** — the renderer must unsubscribe from workspace events
  *before* `ws.dispose()` tears down the emitter and terminates the worker.
  `KonvaRenderer.vue` disposes the renderer in `onBeforeUnmount`, ahead of
  `useWorkspace.provide()`'s `onUnmounted(ws.dispose)`.
- `Workspace.disabled` = `state.disabled || executorState.isProcessing` — gate
  UI during runs so backend back-writes don't re-trigger runs.

## 9. A complete JSON-RPC round trip

```
frontend ──{ "jsonrpc": "2.0", "id": 1, "method": "goldenGraph/listNodeProviders" }──► ws server
frontend ◄─{ "jsonrpc": "2.0", "id": 1, "result": { "providers": [...] } }── ws server
frontend ──{ "jsonrpc": "2.0", "id": 2, "method": "goldenGraph/execute", "params": { snapshot, entryNodeIds, debug } }──► ws server
frontend ◄─{ "jsonrpc": "2.0", "method": "goldenGraph/progress", "params": { "currentNodeId": 1 } }── ws server
frontend ◄─{ "jsonrpc": "2.0", "method": "goldenGraph/handleUpdates", "params": { "updates": [] } }── ws server
frontend ◄─{ "jsonrpc": "2.0", "method": "goldenGraph/progress", "params": { "currentNodeId": 2 } }── ws server
frontend ◄─{ "jsonrpc": "2.0", "method": "goldenGraph/handleUpdates", "params": { "updates": [{ "nodeId": 2, "key": "out", "value": 1 }] } }── ws server
frontend ◄─{ "jsonrpc": "2.0", "id": 2, "result": null }── ws server
```

A cancelled round trip differs only at the end — the user sends the
fire-and-forget Notification mid-run, the run stops at its next node
boundary, and the `execute` Response settles with the Cancelled error:

```
frontend ──{ "jsonrpc": "2.0", "method": "goldenGraph/cancel" }──► ws server
frontend ◄─{ "jsonrpc": "2.0", "id": 2, "error": { "code": -32001, "message": "cancelled" } }── ws server
```

A WebSocket backend sketch: any process can act as the backend by speaking
the same JSON-RPC methods — answer `goldenGraph/listNodeProviders` with the
node providers' schemas, receive the `ExecuteRequest` as `goldenGraph/execute`
params, stream `goldenGraph/progress` / `goldenGraph/handleUpdates`
Notifications, stop the in-flight run on `goldenGraph/cancel`, and reply
`result: null` (a `-32000` error, or a `-32001` Cancelled error when the run
was stopped by a cancel) to settle the run. Implement `ExecutorBackend` on
the frontend to bridge the WebSocket into the `Executor` facade
(`getNodeProviders()` answers the socket, `execute()` forwards the request
and forwards Notifications to `onEvent`, `cancel()` sends the cancel
Notification, resolving/rejecting from the Response).
